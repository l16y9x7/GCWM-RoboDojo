# Agent 交互范式

代码臂采用两层闭环，让模型在动作前规划、动作后检查，而不是连续生成完整动作脚本。

## 任务级闭环

```text
场景理解与任务分解
  → 输出一个有边界的执行脚本
  → 执行并查看图像、状态和程序结果
  → 总结进展、更新里程碑并规划下一步
  → 输出下一段脚本
```

第一次调用工具前，先用简短文字给出任务计划，不调用工具。计划包含：

- **目标**：把用户要求转成最终场景中可检查的结果。
- **场景与不确定项**：只列影响动作选择的已知事实和待确认信息；把视觉估计标成估计，不当作精确坐标或事实。
- **有序里程碑**：按依赖顺序拆分任务。每项写明目标状态和可观察的完成证据；需要抓取、交接、放置等关键状态时，明确其确认标准。
- **动作边界**：说明下一次工具调用只推进到哪个检查点。凡是需要先观察结果再决定的动作，必须分开调用，不能把后续依赖动作预先写进同一脚本。

每次工具返回后，在调用下一工具前先做简短进展汇报，包含：

- **本轮结果**：实际执行了什么，结果是否符合预期。
- **证据与不确定性**：图像、状态或工具返回值能确认什么，哪些还无法确认。
- **里程碑状态**：将相关里程碑标为“未开始”“进行中”“已确认”或“受阻”。只有满足计划中写明的证据标准才能标为“已确认”；命令成功或脚本结束本身不算证据。
- **下一步**：指出要推进的里程碑和下一次调用的动作边界；若证据不足或结果异常，先观察、重新定位、调整或恢复，不执行依赖未确认结果的动作。

新证据改变计划时，简要说明变化并更新受影响的里程碑，无需每轮重述完整计划。汇报只写有用的观察、判断依据、状态和下一步，不输出隐藏推理。失败或不确定的动作不能记作完成。

## 动作级检查点

视觉定位只作为位置估计。抓取和放置都拆成多个工具调用，每个调用只推进到下一个可观察的阶段：

- **抓取**：移动到目标附近并停止，不闭合夹爪；查看结果并校准；确认对齐后，在单独一次工具调用中闭合夹爪；随后先检查夹爪反馈、机器人状态和图像，确认物体确实夹在手中后，才能开始抬起或运输。
- **放置**：夹爪保持闭合，先移动到目标容器附近；查看结果并校准；确认位置可信后再释放；最后观察确认物体已放好。

脚本正常执行或夹爪命令成功都不代表抓取成功。图像或状态不确定时，应先观察、重新定位或调整计划，不继续执行依赖该结果的动作。若当前工具提供 `holding`、夹爪开度等反馈，应结合图像判断；只有夹爪闭合而没有物体持有证据时，不得开始搬运。确认结果不清楚时，保持当前姿势并继续检查，不要把运输动作当作默认的抓取测试。

## 双手协作与交接

两只手交接物品时，必须从物品两侧相对指向并接近。

交接物品时，持物手必须保持夹爪闭合，直到确认接收手已抓稳物品。每个阶段使用单独的工具调用，并在阶段间检查结果：持物手保持不动，接收手移动到交接位置并停下检查；接收手闭合夹爪后，检查图像和可用状态，确认物品确实由接收手抓住；只有确认抓稳后，持物手才能松开。若结果不确定，两手都保持闭合，先观察并调整，不得释放。持物手松开后，再确认物品仍由接收手持有，再让两只手依次退出交接区域。夹爪命令执行成功不等于抓取成功。

## 观察位与多视角

当一只手执行任务、另一只手空闲时，先把“为空闲手建立观察位”列为第一个机器人动作里程碑，再开始执行手的接近或抓取。检查初始图像和两臂状态；若空闲手尚未处于安全、抬高且腕部相机朝向工作区的位置，先在一个独立工具调用中只移动空闲手到合适观察位，不要在同一调用里开始执行手动作；调用返回后检查图像和状态，确认空闲手能观察作业区、不会遮挡目标或进入执行手路径。空闲手留在起始位、回到 `home` 或仅仅避开工作区，都不算完成观察位。若初始观察已确认空闲手处于合适观察位，可直接进入工作阶段。执行手操作期间保持空闲手的观察姿态；若观察位不再安全或妨碍操作，先重新规划并确认新的安全观察位，再继续。观察位须按当前场景选择，不假设固定坐标适用于所有场景。

接近、抓取、抬起、预释放对齐和释放后都检查关键图像。图像附加策略由 `images` 配置控制：`on-motion` 在工具调用发生移动后附加配置相机的当前图像；`on-primitive` 附加该调用中每个状态变更原语结束时的配置相机图像，按执行顺序排列；`on-demand` 不自动附加图像，需用 `robo.show(camera)` 请求；`none` 不自动附加图像。代码通过 `display(image)` 输出的图像会额外附加，不受上述自动策略影响。若需在未移动的调用中观察，或指定视角，可用 `robo.show(camera)`。每个动作阶段返回的图像会随对应工具结果进入对话上下文，模型应跨阶段对照，而不是只看工作手腕相机的单张近景。`on-primitive` 会增加单次调用附带的图像数量，需结合上下文图片上限使用。

### 图片上下文的保留策略

图片应按任务目标的完整动作过程保留，而不是只保留最近一两张观察图。比如“抓起红色方块”是一个目标动作：从目标开始、接近、抓取、抬起到确认抓住的图像都应留在上下文中，方便模型比较动作前后的变化。进入下一个目标（例如把方块放入盒子）后，前一目标的中间过程图通常不再需要；应保留其最终状态图，作为下一目标的场景检查点，并保留任务初始图作为全局参照。

目标边界优先由任务级规划显式标记：模型在工具结果后总结里程碑，并说明当前目标已完成、下一目标是什么。图片归属到当前目标；目标完成时，将该目标的图像组封存为一个检查点，只留最终状态图参与后续请求。失败或未确认的目标仍是当前目标，不能因尝试次数或工具调用边界而提前清理。这样既保留当前目标的完整动作证据，也避免整局运行的所有视觉过程无限累积。

OpenAI runtime 会把初始任务图片以及工具结果附带的图片保留在后续请求中，并按 `max_context_images` 上限（默认 40）从最旧图片开始淘汰。上限按图片计数，而不是按消息或目标计数；当一轮附带多张图时，较早阶段的图可能先被淘汰，即使该目标尚未完成。淘汰只影响后续请求的 transcript，本地运行记录中的图片档案仍保留。Codex/Claude 外部 runtime 的对话历史不由本工具管理。

### 当前实现位置

`src/roboskylar/arms.py` 实现 `on-motion`、`on-primitive`、`on-demand` 和 `none` 四种附图策略；XPolicyLab 部署配置当前使用 `on-primitive`，见 `integrations/xpolicylab/roboskylar/deploy.yml`。`src/roboskylar/openai_runtime.py` 将初始任务图和工具图像加入后续模型请求，并在超过 `max_context_images` 时从请求 transcript 中删除最旧图片；图像文件仍保留在运行记录目录。按目标开始/完成标记分组图像、目标完成后只保留终态图的规则仍是交互建议，当前没有自动实现。

## 提示词的新增部分

下面是新增提示词的规范内容。

```text
# 交互协议

## 模块一：计划与总结范式

采用“观察 → 计划 → 行动 → 复查”的循环。根据实际图像和机器人状态决定下一步，不把动作命令成功当作任务成功。

第一次调用工具前，先用简短文字说明计划，不要在第一条回复中调用工具。前提条件具备时，应一次列出从当前状态到最终目标的完整计划，而不只列下一步。以抓取某个物品并放到某个位置为例，计划应依次包含：

1. 定位目标物品。
2. 到达预抓取位置并确认对齐。
3. 抓取物品并确认抓取成功。
4. 携物移动到目标位置附近并确认到位。
5. 放置物品并确认放置成功。
6. 双侧夹爪完全张开，双手归位，并确认两臂已归位且夹爪完全张开。

完整计划应包括最终目标、已知场景事实与待确认项，并为每个里程碑写明目标状态和可观察的完成证据。适用时，将建立空闲手观察位列为第一个机器人动作里程碑，并将双侧夹爪完全张开、双臂归位及状态确认列在提交之前。若计划所需前提尚不具备（例如还需要观察演示），先计划并补齐前提，再于首次执行任务动作前列出完整任务计划。

每次工具返回后、下一次调用工具前，简短汇报本轮结果、证据与未确定事项，并逐项列出所有里程碑的当前状态及依据；状态使用“未开始”“进行中”“已确认”或“受阻”。每次总结还要判断当前计划是否符合模块二、刚执行的动作是否符合模块三，并分别给出“是”“否”或“不适用”及简短依据。只有符合计划中完成证据的里程碑才能标为“已确认”；命令成功或脚本结束本身不算证据。证据不足或异常时，先观察并调整，不执行依赖未确认结果的动作；需要先观察结果才能决定的动作必须分开调用。计划可随新证据更新。总结只保留有用信息，不输出隐藏推理。

使用以下格式组织计划和总结，按任务删减无关字段：

计划（首次工具调用前；前提具备时列出完整计划）：
- 目标：……
- 场景事实 / 待确认：……
- 完整里程碑计划：按依赖顺序列出全部阶段；每项写明目标状态、确认依据和状态（未开始 / 进行中 / 已确认 / 受阻）
- 若前提不足：先列出补齐前提的步骤；前提满足后再列完整任务计划
- 本次调用边界：只……；返回后检查……

总结（每次工具返回后）：
- 本轮动作与结果：……
- 证据 / 未确定：……
- 计划各里程碑完成情况：逐项列出全部里程碑的状态（未开始 / 进行中 / 已确认 / 受阻）及确认依据
- 计划符合规划原则：是 / 否 / 不适用；依据：……
- 动作符合运动规范：是 / 否 / 不适用；依据：……
- 下一步与调用边界：……

## 模块二：规划原则

当一只手执行任务、另一只手空闲时，先检查初始图像和两臂状态，并把“为空闲手建立观察位”列为第一个机器人动作里程碑。

- 若空闲手已经处于安全、抬高且腕部相机朝向工作区的位置，并且不会遮挡目标或进入执行手路径，可确认观察位后开始任务。
- 否则，在一次独立工具调用中只移动空闲手到适合当前场景的观察位；该调用不得同时开始执行手动作。
- 调用返回后检查图像和状态，确认空闲手能观察作业区、不会遮挡目标，也不会妨碍执行手路径。

空闲手留在起始位、回到 `home`，或只是避开工作区，都不算建立观察位。任务执行期间保持空闲手的观察姿态；若观察位变得不安全或妨碍操作，先重新规划并确认新的安全观察位，再继续。观察位按当前场景选择，不假设固定坐标适用于所有场景。

任务结果确认完成后，将双侧夹爪完全张开并使双臂归位列为最后一个执行里程碑。分别对左右手调用 `set_gripper(arm, robo.OPEN)`，再调用双臂归位；检查机器人状态，确认两只机械臂都已回到 `home` 且两侧夹爪均完全张开后，才能提交任务。任务结果或最终状态任一项尚未确认时，不得提交。

## 模块三：运动规范

### 抓取与搬运

#### 接近目标

先移动到目标附近，并在闭合夹爪前停下。检查图像和机器人状态，必要时重新定位或小幅修正；只有接近位置看起来可信、与目标对齐后，才能继续闭合夹爪。

#### 闭合夹爪并确认抓取

闭合夹爪必须单独调用。调用返回后，先检查夹爪反馈、机器人状态和图像，再决定下一步。只有证据确认目标确实被夹住后，才能开始抬起或运输。

若工具提供 `holding`、实测夹爪开度等状态，应结合图像判断。夹爪闭合或命令执行成功本身不能证明抓取成功。证据不明确时，保持当前姿势，继续观察、重新定位或调整；不要开始运输。

### 放置

保持夹爪闭合，先移动到目的地附近并停下检查。检查图像和机器人状态，必要时修正位置。只有对齐可信后，才能在后续一次独立工具调用中松开夹爪。松开后检查图像和状态，确认物体已成功放置。

### 插入

执行插入时，先让执行手移动到插入位置前的接近位置并停下，不要进入插口。然后在一次独立工具调用中，将另一只手移动到合适的观察位，使其能看到插口和执行手，且不会遮挡目标或妨碍执行手。检查图像和机器人状态，确认执行手及物体已与插口对齐后，才在后续一次独立工具调用中执行插入。若对准情况不确定，先调整或再次观察，不得仅凭命令目标姿态就插入。

### 双臂协作与交接

两只手交接物品时，必须从物品两侧相对指向并接近。

交接物品必须分阶段执行，每个阶段使用单独的工具调用：

1. 持物手保持夹爪闭合，直到确认接收手抓稳物品。
2. 接收手闭合后，检查图像和可用状态，确认物品确实由接收手持有。
3. 确认接收手持稳后，持物手才能松开。
4. 持物手松开后，再确认接收手仍持有物品，然后让两只手依次退出交接区域。

如果任一阶段的结果不确定，两手都保持闭合，先观察或调整。夹爪命令成功不等于接收手已经抓稳物品。

```

## 实现位置

动作闭环规则写在 `src/roboskylar/arms.py` 的 `CELLS_CONTRACT` 和 `PROGRAM_CONTRACT` 中，分别约束持久 Python 会话和独立程序工具。工具执行后返回结果和配置允许的图像，模型据此决定下一阶段；机器人动作本身不会在脚本执行期间调用语言模型。RoboDojo RGB 的移动反馈会附加头部和左右腕部相机图像，其他机器人以各自配置的相机为准。
